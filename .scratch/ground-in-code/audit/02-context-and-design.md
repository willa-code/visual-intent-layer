## Findings

- **CLAIM**: CONTEXT.md:47 "Replacement" — "the published envelope schema still names the field `supersedes`, because a wire name is a compatibility surface rather than a word a Builder-Reviewer reads."
  **CODE**: The current published schema is v0.4 (`src/annotation/envelope.ts:39` sets `schemaVersion: '0.4'`). `schema/envelope-v0.4.schema.json`'s `annotation` definition (lines ~185–260) has no `supersedes`, `replaces`, or `replacedBy` property at all, and `buildBatchEnvelope` (`src/annotation/envelope.ts:44-51`) never serializes `annotation.replaces`/`replacedBy` into the envelope it sends. `supersedes` exists only in the frozen historical `schema/envelope-v0.1.schema.json:106` and is read solely by `src/annotation/migrate.ts` for legacy stored records (confirmed by `src/annotation/store.ts:907-918`, which renames incoming `supersedes`/`supersededBy` to `replaces`/`replacedBy`). The mechanism that actually informs the agent of a Replacement is the `check_in` MCP tool's separate `amendments: Array<{ replacedId, replacementId }>` field (`src/mcp/service.ts:72`, populated at `src/mcp/service.ts:469`), not the envelope.
  **VERDICT**: WRONG
  **FIX**: Rewrite the sentence to name the actual mechanism — e.g. "what the agent was told stays a record; a Replacement travels to the agent as `replacedId`/`replacementId` in the `check_in` result, not as a field on the delivered envelope" — and drop the `supersedes` claim, which no longer describes any live wire surface.

- **CLAIM**: design.md:174 (Annotation state family), design.md:287 (`AnnotationPill` variants), design.md:702 (amendment prose) all list `rejected` as a live Annotation state, e.g. "draft, queued, delivered, acknowledged, resolved, verified, rejected, not-fixed, replaced, obsolete."
  **CODE**: `AnnotationState` (`src/annotation/model.ts:10-19`) has exactly nine values with no `rejected`: `draft | queued | delivered | resolved | acknowledged | verified | not-fixed | replaced | obsolete`. `statePill`/`STATE_CUES`/`stateTone` (`src/ui/components.ts:15-71`) only handle these nine. CONTEXT.md:51 ("Not Fixed") itself states "the retired word **Rejected** reads as Not Fixed," and design.md's own amendment "2026-09-18 — One 'no', and a decision that can be changed" (design.md:702-720) declares "`Reject` retires, `Not Fixed` becomes visible" — but the main-body tables at lines 174 and 287 were never edited to remove it.
  **VERDICT**: STALE
  **FIX**: Delete `rejected` from the three cells at design.md:174, 287, 702 (leave `not-fixed` in place).

- **CLAIM**: design.md:175 "Resolution | matched, recovered, ambiguous, deleted | ..." (main-body §4 table) and design.md:288 `AnnotationRow` "matched, recovered, ambiguous, deleted, advanced."
  **CODE**: `ResolutionLabel` (`src/resolution/model.ts:3`) has six values: `matched | recovered | ambiguous | deleted | state-only | blocked`, both used in shipped UI: `resolutionTone`/`resolutionItem` (`src/ui/components.ts:74-118`) render `state-only` as "May exist only in a state no longer on screen" and `blocked` as "Inside a boundary this surface cannot read" (`src/resolution/model.ts:100-113`). design.md's own last amendment, "A boundary the surface cannot read is stated, not silent" (design.md:895-905), explicitly claims to replace "§4's resolution vocabulary, which had no word between Matched and Deleted," but the actual §4 and §6 rows at lines 175 and 288 were never edited.
  **VERDICT**: STALE
  **FIX**: Update design.md:175 to `matched, recovered, ambiguous, state-only, blocked, deleted` and design.md:288 similarly.

- **CLAIM**: CONTEXT.md:83 "Harness Detection" and CONTEXT.md:87 "Harness Registration" describe pre-write detection of harnesses "from their own configuration locations and their own commands" and a "product's server entry present in a Harness's own native configuration."
  **CODE**: Currently implemented by `src/harness-registry.ts` (`detectHarnessPresence`, `detectHarnesses`, `HARNESS_DESCRIPTORS`) and `src/cli-setup.ts` (`planSetup`, `applySetup`), wired into the `setup` verb in `src/cli.ts:5,45-102`. Per the task's settled decision #1, `src/cli-setup.ts`, `src/harness-registry.ts` and their tests are being deleted, and the `setup` verb goes per decision #5; installation becomes "the human using their own harness-native MCP registrar" — i.e. no product code performs detection or writes a registration afterward.
  **VERDICT**: STALE
  **FIX**: Remove the "Harness Detection" and "Harness Registration" entries (or rewrite them to describe a manual human act using the harness's own registrar, with no product-side detection/write step, if the maintainer wants the vocabulary kept for narrative purposes).

- **CLAIM**: CONTEXT.md:44 "Pass" — "A Pass has a state (open, in flight, ready, closed)"; design.md:172 "Pass | open, in flight, ready, closed | ...".
  **CODE**: `PassState` (`src/annotation/store.ts:32`) has five values: `'open' | 'in-flight' | 'ready' | 'closed' | 'withdrawn'`. `withdrawn` is a first-class, distinctly rendered state — `passStateLabel` (`src/ui/components.ts:184-193`) labels it "Taken back," and `passTone` (`src/ui/components.ts:434-443`) gives it its own tone mapping alongside `closed`. CONTEXT.md's next sentence ("A Pass the agent has not collected may be taken back instead") names the *action* but the parenthetical state enumeration omits the resulting state value.
  **VERDICT**: STALE
  **FIX**: Add "withdrawn" (rendered "Taken back") to the state lists at CONTEXT.md:44 and design.md:172.

- **CLAIM**: design.md:284 (`AnnotationCard`) — "Its target line is a kind icon plus what was pointed at, never the bare kind word, and an Area carries the drawn-boundary glyph."
  **CODE**: `describeTarget()` (`src/ui/app.ts:2102-2107`) is `target.label ?? grounding.accessibleName ?? grounding.semanticRole ?? target.kind` — the final fallback is literally the bare kind word (`element`, `text-range`, or `region`), reachable whenever a target (very plausibly a drawn Area, which typically has no `accessibleName`/`semanticRole`) has none of the earlier fields. `targetLine()` (`src/ui/app.ts:1701-1710`) prepends a `kindIcon` before this text but does not prevent the bare-kind-word fallback in the text itself.
  **VERDICT**: WRONG
  **FIX**: Give `describeTarget` a non-kind-word fallback (e.g. "an area you drew" / "a point you selected") before falling through to `target.kind`, or narrow the doc's claim to "never *only* the bare kind word (an icon always precedes it)" if that reading is intended.

- **Code with no documentation**: `BoundaryRefusal` (`src/ui/artifact/boundary.ts:4`) has a fourth value, `'unloaded-frame'`, distinct from `'policy-blocked-frame'`; it is rendered by `boundaryReasonSentence` (`src/ui/app.ts`, case `'unloaded-frame'` → "lives inside a frame that has not loaded, so there is nothing inside it to find yet") and surfaces in both the row's unresolved sentence and the approval-blocker text. design.md's boundary amendment (design.md:895-905) names only three boundary causes in prose — "a closed shadow root, a cross-origin frame, a frame the content policy never loaded" — and never mentions a frame that simply has not finished loading. This is load-bearing: it is reachable any time a Target lives inside a same-origin frame that hasn't loaded yet, a state distinct from a policy refusal, and it changes what the row/approval-blocker says to the Builder-Reviewer.
