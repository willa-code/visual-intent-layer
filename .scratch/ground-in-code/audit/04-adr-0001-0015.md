## Findings

**Finding 1 — P0 — ADR-0014 describes a mechanism the settled decisions delete in its entirety**
- CLAIM: "`setup` treats a Harness as present when either its own configuration location exists... or its command resolves on `PATH`... A Harness Registration is compared against the entry the installed product would write rather than trusted..." (`docs/adr/0014-union-harness-detection-and-content-verified-registration.md:3`), plus "Harness knowledge becomes a registry of per-harness descriptors... instead of inline conditionals in `cli-setup.ts`." (same file, Consequences).
- CODE: The entire mechanism is live and matches the ADR precisely today — `HARNESSES`, `HARNESS_DESCRIPTORS`, union-of-config-or-command detection in `detectHarnessPresence`/`describeEvidence` (`src/harness-registry.ts:120-172`), and content-verified registration/repair logic in `planSharedFile`, `planCodex`, `planClaudeGlobal`, `planOpencode` (`src/cli-setup.ts:229-244, 331-371, 468-497, 500-556`). The `setup` verb is wired in `src/cli.ts:54-104`.
- VERDICT: STALE (whole ADR dies). Per settled decision 1, `setup`, `src/cli-setup.ts` and `src/harness-registry.ts` (and their tests) are being deleted; the entire subject of ADR-0014 ceases to exist. This is the one ADR in the 0001–0015 range whose mechanism is *fully* retired by the decision, not partially amended.
- FIX: Add a superseding status line ("**Status:** superseded — `setup` and the Harness Registry are deleted; installation is via the user's own harness-native MCP registrar") and move the file to historical/RECORD status. No replacement ADR for the new install path exists yet in 0001–0030 (see "Could not verify").

**Finding 2 — P0 — ADR-0002's Skill half dies with the settled Skill deletion**
- CLAIM: "A thin optional Skill will add proactive trigger policy, the Visual Direction Loop, and host-specific fallbacks without duplicating tool schemas, so explicit use works in MCP hosts that do not support Skills..." (`docs/adr/0002-self-describing-mcp-with-optional-skill.md:3`).
- CODE: `skills/visual-intent/SKILL.md` exists and is installed by `planSkill` (`src/cli-setup.ts:395-411`), gated by `--no-skill` (`src/cli.ts:38,84`) and `pi.skills: ["./skills"]` in `package.json:18-20`.
- VERDICT: STALE. Settled decision 2 deletes `skills/visual-intent/`, the `pi.skills` field, and `--no-skill`. The "optional thin Skill" clause of 0002 has no future referent.
- FIX: Strip the Skill clause; the ADR's surviving content is only "one self-describing model-visible MCP entry tool... keep interface mechanics app-only" — but see Finding 3, that clause is independently wrong against current code.

**Finding 3 — P0 — ADR-0002's "one... entry tool" is contradicted by the current MCP surface, independent of the Skill deletion**
- CLAIM: "The product will expose one self-describing model-visible MCP entry tool..." (`docs/adr/0002-self-describing-mcp-with-optional-skill.md:3`).
- CODE: `listTools()` returns four tools — `open_visual_review`, `check_in`, `get_intent_status`, `acknowledge_intent` (`src/mcp/service.ts:606-673`). ADR-0018 explicitly documents this growth: "A Check-In call becomes part of the tool surface, which blocks the amend, stop and convention tickets." (`docs/adr/0018-steering-is-a-convention-not-a-capability.md:9`).
- VERDICT: WRONG (contradicted by code and by a later ADR that neither amends nor is cross-referenced by 0002). This is not caused by the setup/Skill deletion — it is a pre-existing drift that predates this audit's settled-decisions list.
- FIX: Amend ADR-0002 with a status note pointing to ADR-0018 ("superseded in part: the tool surface is no longer a single entry tool; Check-In became a first-class tool"), or fold 0002 entirely into RECORD once rewritten without the Skill and single-tool claims.

**Finding 4 — P1 — ADR-0012's verb vocabulary is stale against the Annotation/Pass model, with no amendment note**
- CLAIM: "...require the Builder-Reviewer to approve, reject, supersede, or mark the intent obsolete." (`docs/adr/0012-require-human-verification-to-complete-intent.md:3`).
- CODE: `VerificationVerdict = 'approve' | 'not-fixed' | 'obsolete'` (`src/annotation/model.ts:21`); `reject`/`rejected` is explicitly retired and read as `not-fixed` (`src/annotation/store.test.ts:402-403`); ADR-0025 states this in prose: "`Reject` retires and `Not Fixed` is the single verdict... `rejected` records and `reject` verdicts are read as Not Fixed" (`docs/adr/0025-a-verdict-is-reversible.md:5,38`). "Supersede" is likewise not a per-Annotation verdict any more; superseding now happens via the Pass-level "Another Pass"/Replacement mechanism (`docs/adr/0019-a-pass-is-the-unit-of-review.md:17`, `docs/adr/0026-another-pass-opens-a-new-pass.md`).
- VERDICT: STALE. Compare to sibling ADRs 0003, 0004, 0008, 0015, which all carry an explicit "amended by / superseded by" header — 0012 carries none, so a reader has no signal that "reject" and "supersede" are retired words.
- FIX: Add a status header to 0012 pointing at ADR-0019/0025/0026 ("verb vocabulary superseded: reject → Not Fixed, supersede → Another Pass/Replacement at the Pass level").

## Code with no documentation

- **`scripts/check-bins.js:13-24`** — a release-time check that reads the packaged root `mcp.json` and fails the build if its pinned package version/tag doesn't match `package.json`. Root `mcp.json` (`/mcp.json:1-9`) pins `visual-intent-layer@0.3.0-next.3` via `npx`. This mechanism is named in the settled decisions ("the packaged repo-root mcp.json is being deleted along with its release-time check") but no ADR in 0001–0015 (or, from my search, elsewhere) documents why this file/check existed in the first place — it is load-bearing today (an active build-gate) but has zero ADR coverage, so its removal isn't traceable to any decision record being amended. Worth a line in whichever ADR or changelog absorbs decision 3.
- **`src/host/capabilities.ts:1-9,11-17`** — the `embeddedUI`/`subscriptions` negotiation surface is exercised by real code but the *values* it can take and their downstream effect (`describeCapabilities`, `capabilities.ts:19-22`) are described only in ADR-0008's amendment note in passing; no ADR spells out the two-flag contract as its own decision. Likely fine to leave as an implementation detail rather than a gap requiring a new ADR — flagged for completeness only.
