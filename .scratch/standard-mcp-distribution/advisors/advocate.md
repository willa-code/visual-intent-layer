# User Advocate — standard-mcp-distribution

## 1. Harness Detection / Harness Registration in CONTEXT.md
Delete both. CONTEXT.md documents words the product itself says, in code and surface — Honesty is "the product saying only what it can know." Once `harness-registry.ts`/`cli-setup.ts` are gone, the product doesn't detect or register anything; the human's act with their Harness's own registrar happens entirely outside our reach, in that Harness's vocabulary, not ours. Naming it in our glossary is guessing at someone else's process, the opposite of the precision VISION asks for. The README's install table already carries the right words ("registrar," "own mechanism"); no glossary entry is needed for an act we never witness.

## 2. Version self-report placement
Every `open_visual_review` result, not only on error. A Builder-Reviewer reports "odd behaviour," not "an error" — many failures this exists for (a wrong-feeling layout, a bad resolution) never throw. Gating the version behind an error path asks the product to predict which call is worth citing before the human has noticed anything; by the time they have, it's too late to add it retroactively. This is a machine-channel field, not chrome a human reads by default, so Concise's "never spent by default" doesn't bind it. Every result is the honest, low-effort choice.

## 3. describeTarget's last-resort fallback
Fix it — and scope it wider than the spec frames. Verified in `src/ui/app.ts:2102–2106`: the wire kind for a Builder-Reviewer-drawn Area is literally `'region'` (`src/annotation/migrate.ts:6`), and CONTEXT.md's Area entry puts "Region" on its own Avoid list. The current fallback shows the Builder-Reviewer, in their own card, the exact word CONTEXT.md forbids for that concept — a live violation, not hypothetical. Read it as human words. But the same fallback chain (`target.kind`) also bottoms out at bare `'element'`/`'text-range'` when those targets lack a label — equally raw, just not on an explicit Avoid list. Fixing only "region" relocates the problem rather than closing it. This is a small, self-contained fix; it doesn't need the distribution change's tests, but it shouldn't wait indefinitely for "its own" spec while a defined Avoid-list word keeps shipping.

## (a) Decision I'd reverse: the Skill's judgment content vanishing with it
Removing the Skill mechanism on absence of evidence is honest. But `skills/visual-intent/SKILL.md`'s "When visual direction beats prose" section names four concrete triggers no tool description states: naming a thing by location, comparing visible things, a prose correction that already missed, wanting to verify visually rather than read a diff. `open_visual_review`'s description (`src/mcp/service.ts:614`) only keeps the compressed conclusion — "when pointing beats prose" — not the heuristics that get an agent there before it has already decided to inspect that tool. The harmed party is the agent an implicit request never reaches. Before deleting the Skill, port those four triggers into the tool description; don't let content that outlives the mechanism disappear with it.

## (b) Silent on: first-attempt failure with no diagnostic
The spec deletes `--status` along with `setup`. The Builder-Reviewer's first attempt becomes: paste the registrar command, trust it, open their Harness. When the tool doesn't appear — stale binary, wrong scope, typo — there is no product-side way to ask what *visual-intent* thinks is registered, because the product now knows nothing about any Harness's config. "A fresh-install check is a named human step" (Testing Decisions) covers the Lever, not this person's actual failure mode. That gap is created by this change and belongs in it.
