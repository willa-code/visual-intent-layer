# An automated Verification Run is not Verified Intent

The repository now uses "verification" for two different actors: the Builder-Reviewer who completes an Annotation in Verify, and the coding agent that proves a mechanism works with a Verification Run. A green Verification Run looks exactly like an approval, so every place an agent reads the word — the glossary, the skill body and the run record — states the boundary rather than leaving it to be inferred. A Verification Run establishes Mechanical Verification: evidence that the mechanism behaved as specified, covering the user paths it drove and naming the ones it could not reach. It does not establish Verified Intent, does not complete an Annotation, and does not judge whether the resulting direction is good. Only a Builder-Reviewer, reviewing a resulting revision by hand, completes an Annotation.

**Considered Options:** Letting a passing run mark Annotations verified was rejected because it would let the harness manufacture the one act the product reserves for a human. Renaming the agent-facing sense to something outside "verification" entirely was rejected as a losing battle with ordinary usage and because the run genuinely does verify a mechanism. Keeping the boundary implicit was rejected because a green run is the most likely way this work damages the product's credibility.

**Consequences:** The glossary gains Verification Run and Mechanical Verification, both with _Avoid_ lines. The skill body restates the boundary where an agent reads it. The run record reports coverage and outcome — clean, changed, blocked, or aborted — and never a verdict on an Annotation. This is hard to reverse once agents and the maintenance pass treat a run record as durable evidence, which is why the decision is recorded now rather than assumed.
