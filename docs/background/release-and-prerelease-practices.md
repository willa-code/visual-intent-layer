# npm Release, Dist-Tag, and Pre-Release Practices

Research snapshot: 2026-09-15. Sources are the semver 2.0.0 spec, npm documentation (`docs.npmjs.com`), the npm CLI source and release notes (`npm/cli`), the live npm registry API, and GitHub's own docs; plus the first-party release docs of React, TypeScript, Next.js, Angular, Vue, and Node. No shell access was available in this run, so published dist-tags were read from the registry API (`https://registry.npmjs.org/-/package/<pkg>/dist-tags`) instead of `npm view <pkg> dist-tags`.

## Executive conclusion

npm itself defines exactly one tag, `latest`, and deliberately attaches no meaning to any other tag ([npm-dist-tag](https://docs.npmjs.com/cli/v11/commands/npm-dist-tag/)); everything else — `next`, `beta`, `rc`, `canary`, `experimental` — is ecosystem convention that real projects implement inconsistently. `next` is the most widespread pre-release tag, but it is a convention, not a standard, and several majors use `canary`/`beta`/`rc` instead. For this repo the practical consequence is sharper: with npm ≥ 11 (the workflow installs `npm@latest`), `npm publish` **hard-fails** when `package.json` carries a pre-release identifier and no `--tag` is passed ([npm 11.0.0 release notes](https://github.com/npm/cli/releases/tag/v11.0.0)), so a GitHub pre-release today would break the publish job rather than tag a `next` build. Promotion should be a new stable version (`0.3.0-next.3` → `0.3.0`), not a dist-tag move, and rollback should be fix-forward plus `npm deprecate`, since versions are immutable.

## 1. Dist-tag conventions

**Claim:** `latest` is the only tag npm defines; `next` is the most common conventional pre-release tag, but the majors disagree. **Sources:** [npm-dist-tag](https://docs.npmjs.com/cli/v11/commands/npm-dist-tag/), [Adding dist-tags to packages](https://docs.npmjs.com/adding-dist-tags-to-packages/), npm registry API (snapshot 2026-09-15). **Support:** direct evidence. **Confidence:** high.

npm's CLI docs say it plainly: "Publishing a package sets the `latest` tag to the published version unless the `--tag` option is used"; "By default, `npm install <pkg>` (without any `@<version>` or `@<tag>` specifier) installs the `latest` tag"; "The `next` tag is used by some projects to identify the upcoming version"; and "Other than `latest`, no tag has any special significance to npm itself." The docs also state that tags share a namespace with versions, that a tag interpretable as a semver range is rejected, and recommend tag names that do not begin with a digit or `v` (the CLI enforces this: `Tag name must not be a valid SemVer range`) — [npm/cli `lib/commands/publish.js`](https://raw.githubusercontent.com/npm/cli/latest/lib/commands/publish.js). `npm install pkg@<tag>` is the documented way to resolve a tag.

First-party corroboration: React documents `latest`, `canary`, and `experimental` as its three channels and states prereleases are "published with the `canary` tag" / "`experimental` tag on npm" ([React versioning policy](https://react.dev/community/versioning-policy)); TypeScript tells users to `npm install -D typescript@next` for nightlies ([TypeScript nightly builds](https://www.typescriptlang.org/docs/handbook/nightly-builds)); Angular documents "Next" (`8.1.0-next.0`) and "Release candidate" (`8.1.0-rc.0`) pre-releases as first-class stages ([Angular versioning and releases](https://angular.dev/reference/releases)); Vue documents `alpha`/`beta`/`rc` phases and installs via `@alpha`/`@beta`/`@rc` ([Vue releases](https://vuejs.org/about/releases)); Next.js documents `stable` and `canary` channels with `next@canary`, and its own RC posts use `next@rc` ([Next.js release channels](https://github.com/vercel/next.js/blob/canary/contributing/repository/release-channels-publishing.md)). Node.js is the counterexample: its npm `node` package carries no pre-release tag at all.

**Researcher inference:** `next` is the safest conventional choice for a single pre-release channel, because it is the tag both npm's docs name explicitly and the tag used by TypeScript, Angular, eslint and React (as one of several). `canary` implies continuously published builds from `main`, and `experimental` implies unstable/flagged APIs (React and Vue both use it that way) — neither fits a hand-cut beta of a small library.

## 2. Pre-release version identifiers

**Claim:** `-next.0`, `-beta.0`, `-rc.0` are conventional prerelease identifiers; semver gives prereleases lower precedence and they do not satisfy plain ranges; and npm 11+ requires `--tag` for a prerelease publish. **Sources:** [semver 2.0.0 §9/§11](https://semver.org/spec/v2.0.0.html), [npm/node-semver README](https://github.com/npm/node-semver), [npm publish source](https://raw.githubusercontent.com/npm/cli/latest/lib/commands/publish.js), [npm 11.0.0 notes](https://github.com/npm/cli/releases/tag/v11.0.0). **Support:** direct evidence. **Confidence:** high.

Semver §9: "Pre-release versions have a lower precedence than the associated normal version… A pre-release version indicates that the version is unstable and might not satisfy the intended compatibility requirements as denoted by its associated normal version." §11.3: `1.0.0-alpha < 1.0.0`; §11.4 orders identifiers numerically-then-lexically, so `1.0.0-alpha < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0`. Numeric identifiers must not have leading zeroes. npm's own semver implementation adds the range rule: a prerelease "will only be allowed to satisfy comparator sets if at least one comparator with the same `[major, minor, patch]` tuple also has a prerelease tag" — so `^0.3.0` never picks up `0.3.0-next.1`.

`--tag` requirement: npm 11.0.0's breaking-changes list states "When publishing a package with a pre-release version, you must explicitly specify a tag" ([v11.0.0](https://github.com/npm/cli/releases/tag/v11.0.0), shipped via [npm/cli#7910](https://github.com/npm/cli/pull/7910)). The current source throws `You must specify a tag using --tag when publishing a prerelease version.` when the version has a prerelease and the `tag` config is default (not from `publishConfig.tag`). npm 11 also refuses to implicitly apply `latest` when an already-published, non-prerelease, non-deprecated version is higher: `Cannot implicitly apply the "latest" tag because previously published version X is higher than the new version Y.` Note for promotion: the CLI computes that "highest version" **excluding prereleases**, so publishing `0.3.0` after `0.3.0-next.3` sets `latest` normally.

## 3. Pre-1.0 versioning

**Claim:** semver defines `0.y.z` as "initial development… anything MAY change at any time", so the minor is effectively the breaking boundary before 1.0.0; npm's own guidance instead recommends starting at `1.0.0`. **Sources:** [semver §4, §5, FAQ](https://semver.org/spec/v2.0.0.html), [npm: About semantic versioning](https://docs.npmjs.com/about-semantic-versioning/). **Support:** direct evidence (both), plus one researcher inference. **Confidence:** high.

Semver §4: "Major version zero (0.y.z) is for initial development. Anything MAY change at any time. The public API SHOULD NOT be considered stable." §5: "Version 1.0.0 defines the public API." §6–8 are conditioned on `x > 0`, so the patch/minor/major rules formally apply only from 1.0.0 onward. The spec's FAQ says: "The simplest thing to do is start your initial development release at 0.1.0 and then increment the minor version for each subsequent release", and "If your software is being used in production, it should probably already be 1.0.0."

npm's docs give the opposite default: "we recommend starting your package version at `1.0.0`" with the conventional patch/minor/major table, and "If you introduce a change that breaks a package dependency, we strongly recommend incrementing the version major number". npm docs do not describe a `0.x` convention.

**Researcher inference:** the operative pre-1.0 convention in the ecosystem is semver §4 read as "minor = breaking boundary": feature = minor, fix = patch, breaking = minor (promote to major at 1.0.0). That is the only reading consistent with §4's explicit "anything MAY change" and with §6–8 excluding `x = 0`; it also matches how consumers write ranges pre-1.0 (`^0.2.0` is caret-locked to `0.2.x` in node-semver, so minor bumps are the only ones consumers must review). npm's `1.0.0`-first recommendation is guidance for a library with dependents, which this package (no users) does not yet have.

## 4. Promotion: new stable version vs. re-pointing `latest`

**Claim:** promotion should publish a new stable version of the same target; dist-tags are movable but re-pointing `latest` at a prerelease violates the spirit of the stable channel. **Sources:** [npm-dist-tag](https://docs.npmjs.com/cli/v11/commands/npm-dist-tag/), [Adding dist-tags](https://docs.npmjs.com/adding-dist-tags-to-packages/), [semver §3](https://semver.org/spec/v2.0.0.html), [npm/node-semver](https://github.com/npm/node-semver), [npm/cli publish source](https://raw.githubusercontent.com/npm/cli/latest/lib/commands/publish.js). **Support:** mixed — mechanism is direct evidence; the recommendation is researcher inference from documented behaviour. **Confidence:** high on mechanics, medium on "best practice" (npm does not prescribe promotion).

Mechanics: dist-tags are **movable** (`npm dist-tag add <pkg>@<version> <tag>`, `npm dist-tag rm`, `npm dist-tag ls`; the docs' own example is `npm dist-tag add example-package@1.4.0 stable`), while **versions are immutable** — semver §3: "Once a versioned package has been released, the contents of that version MUST NOT be modified." So both moves are technically available:

- **Publish the new stable version** (`0.3.0-next.3` → `0.3.0`). Pros: the stable artifact gets its own tarball, its own provenance/attestation bound to its source commit, and a version string consumers can range-match; npm sets `latest` to it implicitly (prereleases are excluded from the CLI's highest-version check). Cost: one extra publish, and the code must be identical to what was validated (ideally the same commit/tag).
- **Re-point `latest`** (`npm dist-tag add visual-intent-layer@0.3.0-next.3 latest`). Pros: one command, no second publish. Cons: `latest` now resolves to a version string that is semver-prerelease, so `npm install pkg` installs an artifact that `^0.3.0` ranges and `npm update` will never select (node-semver's comparator-tuple rule); the package metadata still advertises instability; and the eventual `0.3.0` publish then makes `latest` jump again, so consumers on the intermediate `latest` can silently skip a version.

npm documents the tag mechanism but gives no promotion guidance; the closest thing to guidance is semver §3 plus the FAQ's "it is unacceptable to modify versioned releases" ([semver FAQ](https://semver.org/spec/v2.0.0.html)). **Researcher inference:** treat promotion as "the prerelease was a rehearsal for an exact version" — publish `0.3.0` from the same commit as `0.3.0-next.3`, and never point `latest` at a prerelease. A reusable pattern when the RC and the stable differ only in the prerelease suffix: after validating `0.3.0-next.3`, drop the suffix; do not re-suffix or re-cut unless the code changed.

## 5. Failure and rollback policy

**Claim:** you cannot meaningfully unpublish or republish a bad version; the documented remedy is fix-forward plus `npm deprecate`, with a dist-tag move as an emergency stopgap. **Sources:** [npm Unpublish Policy](https://docs.npmjs.com/policies/unpublish/), [npm-unpublish](https://docs.npmjs.com/cli/v11/commands/npm-unpublish/), [Deprecating packages](https://docs.npmjs.com/deprecating-and-undeprecating-packages-or-package-versions/), [npm-publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/), [semver FAQ](https://semver.org/spec/v2.0.0.html). **Support:** direct evidence. **Confidence:** high.

- Immutability: "Registry data is immutable, meaning once published, a package cannot change"; a `name@version` pair "can never be used again, even if it is removed with `npm unpublish`"; publishing a version that already exists fails.
- The 72-hour window, precisely: "For newly created packages, as long as no other packages in the npm Public Registry depend on your package, you can unpublish anytime within the first 72 hours after publishing" — and the phase "How to unpublish" describes it as the standard path, it is not a general undo. After 72 hours unpublishing requires **all** of: no dependents, fewer than 300 downloads in the last week, and a single owner/maintainer. Unpublish cannot be reversed, and unpublishing the whole package blocks republishing that name for 24 hours.
- Recommended remedy: "We strongly recommend deprecating packages or package versions instead of unpublishing them, because unpublishing removes a package from the registry entirely, meaning anyone who relied on it will no longer be able to use it, with no warning." Concretely `npm deprecate <pkg>@<version> "<message>"` prints the message on install and on the package page, keeping the artifact downloadable so lockfiles keep resolving.
- Fix-forward is also semver's instruction: "As soon as you realize that you've broken the Semantic Versioning spec, fix the problem and release a new minor version that corrects the problem."
- Guardrail worth knowing: the CLI will not implicitly move `latest` backwards (`Cannot implicitly apply the "latest" tag because previously published version X is higher than the new version Y`) — a deliberate lower-version publish needs an explicit `--tag`.

For this repo there is a genuine 72-hour window (package created recently, no dependents, single owner), so a truly catastrophic `0.2.x` could still be unpublished — but it is a one-shot, irreversible, ecosystem-hostile action and should be treated as a last resort behind fix-forward + deprecate.

## 6. GitHub Actions mechanics

**Claim:** `release: published` is the correct trigger for a workflow that must see both stable and pre-releases (as this repo has), branching on the `prerelease` boolean; trusted publishing needs `id-token: write` on a GitHub-hosted runner, a workflow filename matching the npm configuration, and a matching `repository.url`. **Sources:** [About events that trigger workflows](https://github.com/github/docs/blob/main/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md), [Managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [REST API: releases](https://docs.github.com/en/rest/releases/releases), [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/), [npm provenance](https://docs.npmjs.com/generating-provenance-statements/). **Support:** direct evidence. **Confidence:** high on the trigger and permissions; medium on the exact expression (see below).

- The `release` event's activity types are `published`, `unpublished`, `created`, `edited`, `deleted`, `prereleased`, `released`. GitHub's own note: "The `prereleased` type will not trigger for pre-releases published from draft releases, but the `published` type will trigger. If you want a workflow to run when stable *and* pre-releases publish, subscribe to `published` instead of `released` and `prereleased`." (added in [github/docs#5769](https://github.com/github/docs/pull/5769)). The repo's `on: release: types: [published]` is therefore exactly the documented pattern for seeing prereleases.
- The release object carries a boolean `prerelease`: documented as "`prerelease` boolean: `true` to identify the release as a prerelease, `false` to identify the release as a full release" in the release create/edit API and present in the returned release JSON ([REST releases](https://docs.github.com/en/rest/releases/releases)); the Actions docs point the event's payload at that same release object. **Missing evidence:** GitHub's Actions docs give no worked `if: github.event.release.prerelease` example in the `release` section, so the expression form is inferred from the documented payload field plus the `github.event` context (which exposes the webhook payload). Practically, branch with `if: ${{ !github.event.release.prerelease }}` for the stable publish step and `if: ${{ github.event.release.prerelease }}` (or `== true`) for a prerelease step, and never rely on `github.event.release` when the workflow can also run on other events (`push`, `workflow_dispatch`), where the field is null.
- Marking a pre-release is a GitHub-side flag ("This is a pre-release" in the releases UI, or `gh release create … --prerelease`), and it can be flipped later without touching the tag; drafts and prereleases cannot be set as the repository's "latest" release.
- Trusted publishing requirements ([npm docs](https://docs.npmjs.com/trusted-publishers/)): `permissions: id-token: write` ("The critical requirement is the `id-token: write` permission"), a GitHub-**hosted** runner, the workflow filename matching the trusted-publisher config including `.yml` (case-sensitive), and `repository.url` in `package.json` matching the GitHub repo exactly. Troubleshooting notes that `workflow_call`/`workflow_dispatch` wrap cases validate the *calling* workflow's name, and that `id-token: write` must be granted to both parent and child workflows.
- Provenance: trusted publishing from GitHub Actions generates attestations automatically — "This happens by default—you don't need to add the `--provenance` flag"—so `--provenance` in this repo's workflow is redundant but harmless. The provenance docs still describe the `--provenance` + `id-token: write` + public `repository` combination as the supported manual path, and note `--access public` is needed for a first publish.

## Recommendation for visual-intent-layer

1. **Keep `release: published` as the only trigger**, and split the publish step on the payload rather than adding a second event.
2. **Add a pre-release channel now, while there are no users.** Recommended: prerelease versions `0.X.Y-next.N` published with `npm publish --tag next`. This is required, not optional: the workflow installs `npm@latest`, so a `-next.0` version without `--tag` fails the job outright (npm ≥ 11). A `next` step guarded by `if: ${{ github.event.release.prerelease }}` and a stable step guarded by `if: ${{ !github.event.release.prerelease }}` (stable step keeps today's `npm publish --access public`) covers both paths in one workflow. Do not modify the workflow in this research task — this is the change set to implement separately.
3. **Adopt the pre-release naming convention** `0.X.Y-next.N` for betas, reserving `-rc.N` for the release candidate that is byte-identical to the intended stable, and keeping plain `X.Y.Z` for stable. Document the channel on the npm page (`npm install visual-intent-layer@next`) and in the README.
4. **Pre-1.0 versioning rule to document:** while on `0.x`, feature = minor, fix = patch, breaking = minor; `0.3.0-next.N` is the preview of `0.3.0`; go `1.0.0` when the envelope/MCP surface is something others can depend on (semver §5 / npm's "should probably already be 1.0.0"). Note npm's generic recommendation to start at `1.0.0` and explain why this repo deliberately stays pre-1.0.
5. **Promotion = publish `0.3.0` from the same commit as the validated `0.3.0-next.3`.** `latest` then advances implicitly (prereleases are excluded from the CLI's highest-version check). Avoid `npm dist-tag add … latest` on a prerelease — it hands `npm install` a version that plain ranges will never select.
6. **Rollback policy to write down:** fix-forward with a new patch/minor; `npm deprecate visual-intent-layer@<bad-version> "<message>"` for anything users may already have installed; a dist-tag move to the last good version is an emergency stopgap only; unpublish only inside the 72-hour window and only if the release is actively harmful (one-shot, irreversible, blocks reuse of that version number).
7. **CI hardening to note (not implement here):** keep `repository.url` exactly `git+https://github.com/willa-code/visual-intent-layer.git` (trusted publishing validates it), keep the workflow filename `.github/workflows/publish.yml` matching the npm config, keep `runs-on: ubuntu-latest` (GitHub-hosted required), and treat `--provenance` as optional since trusted publishing adds attestations automatically. Consider `npm stage publish` (requires npm ≥ 11.15.0 / Node ≥ 22.14.0) if a 2FA review gate before going live is ever wanted — it is also the documented way to add an approval step to CI publishes.

## Contradictions

- **npm vs. semver on pre-1.0:** npm's semantic-versioning page recommends starting at `1.0.0` and gives no `0.x` convention; semver §4 defines `0.y.z` as initial development where anything may change. These are not strictly contradictory (npm is guidance, semver is spec) but they point in different directions for a library with no users; recorded rather than silently resolved ([npm](https://docs.npmjs.com/about-semantic-versioning/) vs [semver](https://semver.org/spec/v2.0.0.html)).
- **Tag conventions vs. truth:** `next` is repeatedly called "the" pre-release tag in secondary writing, while the registry shows React/Next.js primarily on `canary`, Vue on `beta`/`rc`, and Node on no prerelease tag at all. The registry is treated as the evidence.

## Missing evidence

- GitHub's Actions documentation does not publish a worked example using `github.event.release.prerelease` in a `release`-triggered workflow; the claim that the field is populated rests on the documented release object payload (REST/webhook) and the `github.event` context, not on an explicit Actions-docs example.
- npm does not document a promotion procedure at all (no "promote a prerelease" page found); the recommendation in §4 is inferred from documented tag mechanics plus semver §3.
- The npm publish/dist-tag docs pages (v11) do not mention the prerelease `--tag` requirement at all; that behaviour is evidenced by the npm 11.0.0 release notes and current CLI source instead. Treat the CLI as the authority.
- Node.js's npm package shows no `next` tag; whether Node pre-releases are ever published to npm under another tag was not confirmed (its release docs discuss nodejs.org builds and `vN-lts` dist-tags).
- `npm view` output could not be produced (no shell access); all registry data is from the registry HTTP API and reflects 2026-09-15.

## Open questions

- Should the stable step add `--tag latest` explicitly, or rely on npm's implicit `latest` (and its "highest version excluding prereleases" check)? Implicit is documented behaviour, explicit is self-documenting and fails loudly if the check ever changes.
- Is a GitHub-side prerelease release also the right place to attach release notes, or should `next` builds be cut from tags without a GitHub release (avoiding the `release: published` path entirely)?
- Does `0.3.0-next.N` published with `--tag next` interact with the repo's `prepack` build script or `files` list in any way that requires a package-contents check before the stable cut?
- Would the maintainer prefer enabling npm's staged publishing (2FA approval gate) for the stable channel given trusted publishing is already configured?
